# 07 — Operations and validation

This layer describes the supported bootstrap, reconciliation, recovery, and validation path. It does not own platform configuration; it proves the repository can recreate and operate that configuration. Host OS, tool, capacity, and network prerequisites are declared in the root [README](../../README.md#prerequisites).

## Bootstrap order

```text
fresh checkout
      │
      ▼
┌──────────────────────────────┐
│ 1. Foundation                │
│ make cluster-up              │
│ make cluster-validate        │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. Edge + trust              │
│ make edge-up                 │
│ Vault init / unseal          │
│ make edge-up                 │
│ make edge-validate · 1st run │
│ make edge-smoke              │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. Operator credentials      │
│ GitHub + Docker Hub → Vault  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. Platform services         │
│ make jenkins-up              │
│ make observability-up        │
│ make observability-smoke     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. Application               │
│ bootstrap registry identity  │
│ lab-build → lab-deploy   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 6. Admission policy          │
│ registry auth + image + Helm │
│ server-side dry-run checks   │
└──────────────┬───────────────┘
               ▼
        end-to-end proof
```

Run commands from the repository root.

Before a clean rebuild, retain the Vault Raft data, the matching operator-held unseal key, an authorized Vault token, the local CA, and the GitHub/Docker Hub credentials listed below. The host operator also needs sudo access. A webhook image digest must be published before policy installation. An init file for a different Vault store cannot unseal this one.

## 1. Foundation

```bash
make cluster-up
make cluster-validate
```

Reapply the Git-managed cluster play when required:

```bash
vagrant provision node-3
```

A manual SSH or `kubectl` repair is diagnostic only. If the fix must survive rebuild, encode it in the owning role or manifest.

## 2. Edge and Vault

First reconciliation prepares the host services and stops when Vault requires operator initialization.

```bash
make edge-up
VAULT_INIT_OUTPUT=/secure/absolute/path/vault-init.json make vault-init
make vault-unseal
make edge-up
make edge-validate
make edge-smoke
```

On the first build, `edge-validate` is intentional: it exercises the full DNS/TLS integration and establishes the retained `stage3.lab.test` backend that `edge-smoke` checks. Subsequent reconciliations normally use `make edge-up && make edge-smoke`.

`vault-init.json` contains root-of-trust material. Keep it outside the repository with restrictive permissions and move it to protected operator storage.

After a host reboot, Vault is sealed again. Recovery is explicit:

```bash
make vault-unseal
make edge-up
```

## 3. External credentials

The operator supplies external account values; the repository defines where they are consumed.

| Vault path | Fields | Consumer |
|---|---|---|
| `secret/ci/github` | `username`, `token` | Jenkins SCM checkout and commit status |
| `secret/ci/dockerhub` | `username`, `token` | CI image publication |
| `secret/runtime/dockerhub` | `username`, `token` | Kubernetes private image pull |

With Vault unsealed and an authorized token active:

```bash
export VAULT_ADDR=https://127.0.0.1:8200

vault kv put secret/ci/github \
  username="$GITHUB_USERNAME" \
  token="$GITHUB_TOKEN"

vault kv put secret/ci/dockerhub \
  username="$DOCKERHUB_USERNAME" \
  token="$DOCKERHUB_TOKEN"

vault kv put secret/runtime/dockerhub \
  username="$DOCKERHUB_USERNAME" \
  token="$DOCKERHUB_TOKEN"
```

Prefer environment injection from the operator's local secret manager instead of typing token literals into shell history.

Jenkins admin credentials are generated by the Jenkins reconciliation path and stored in Vault when absent.

## 5. Application registry identity

Before private application images can be pulled, create the namespace-specific Vault identity:

```bash
export VAULT_ADDR=https://127.0.0.1:8200
./app/k8s/bootstrap-registry-auth.sh
```

Flow:

```text
Vault · secret/runtime/dockerhub
             │
             ▼
application Vault AppRole
             │
             ▼
Vault Secrets Operator
             │
             ▼
default/dockerhub-registry
             │
             ▼
Deployment imagePullSecrets
```

Normal application deployment then occurs through `lab-build` → `lab-deploy` as described in [05 — Delivery](../05-delivery/README.md).

## 6. Admission policy

The webhook image must be published before chart installation. The `policy-system` namespace also needs registry pull auth.

```bash
helm upgrade --install resource-requests-webhook \
  policies/resource-requests-webhook/helm/resource-requests-webhook \
  --namespace policy-system \
  --create-namespace \
  --set image.repository=docker.io/atakangul/resource-requests-webhook \
  --set image.digest=sha256:<published-digest>
```

Admission verification uses server-side dry-run. See [Admission policy](../06-governance-resilience/admission-policy.md).

After the application release and admission policy are installed, run `make e2e-validate`.

## Validation model

Validation consumes the running system. It never silently repairs it.

```text
Git desired state
       │
       │ reconcile
       ▼
running system
       │
       ├──► cluster validation
       ├──► container validation
       ├──► edge smoke / deep validation
       ├──► observability smoke
       ├──► application runtime checks
       ├──► immutable delivery identity
       └──► admission allow / deny tests
```

Normal checks:

```bash
make cluster-validate
make container-validate
make edge-smoke
make observability-smoke
```

Use `make edge-validate` when deeper DNS/TLS/create-delete integration needs to be exercised.
`make e2e-validate` composes cluster, edge, and observability checks, then verifies the installed Jenkins, application, metrics, logs, and admission path. Run it after the webhook and application release are installed; it does not install or repair components.

## Final invariants

A complete environment should satisfy all of these:

- three Kubernetes nodes are Ready;
- Pod CIDR is `10.60.0.0/16` and Service CIDR is `10.70.0.0/16`;
- `*.lab.test` resolves through BIND and ingress uses `192.168.56.200`;
- HTTPS is trusted through the local CA/wildcard certificate path;
- Jenkins controller is on node-3 with zero executors;
- CI and CD agents run on node-3;
- Prometheus, Grafana, AlertManager, Elasticsearch, and Fluent Bit are healthy;
- `sample-java-app` has four Ready replicas spread across node-2 and node-3;
- the application responds through `https://app.lab.test`;
- the deployed application image is the immutable digest emitted by CI;
- a valid Deployment passes admission;
- a Deployment missing CPU or memory requests is rejected.

## Recovery pattern

Use the owning reconcile path first:

| Failure | Recovery |
|---|---|
| Vault sealed | `make vault-unseal && make edge-up` |
| edge drift | `make edge-up && make edge-smoke` |
| Jenkins drift | `make jenkins-up` |
| observability drift | `make observability-up && make observability-smoke` |
| application release issue | identify last known-good commit + digest; redeploy through delivery path |

Do not preserve a UI edit, one-off Helm command, or manual cluster mutation as long-lived state.

## Clean rebuild proof

Reproducibility is not proven by a working cluster. It is proven when a clean environment can be recreated from the repository plus the documented operator-held secrets.

```text
working environment
        │
        ▼
commit repository state
        │
        ▼
make destroy
        │
        ▼
fresh checkout + fresh VMs
        │
        ▼
run documented bootstrap only
        │
        ▼
run final invariants
        │
   ┌────┴────┐
   │         │
 pass       fail
   │         │
   ▼         ▼
reproducible  missing step / automation defect
              │
              ▼
         fix Git/docs
              │
              └──────────────► repeat clean rebuild
```

If rebuilding requires an undocumented package install, copied secret, node edit, or cluster command, the rebuild has found a documentation or automation defect. Fix that defect and repeat the clean rebuild.
